# 串口型 USB2CAN 协议笔记（55 AA 帧）

> 适用：达妙 **DM-USBCU1 / USB2CAN V2.x** 一类 USB-CDC 转 CAN 模块，以及桌面上的 `USB2CAN_2.0.0.3.exe`、`DMTool-v2.1.9.4.exe`。
> 不适用：USB2CANFD_S/D / LinkX4C（那套走 libusb + `dmcan-sdk`）。
> 状态：协议主体来自官方 DM-USBCU1 文档、官方示例和 `DM_CAN.py`；CRC 与个别偏移仍需真机/抓包确认。

## 1. 串口参数

| 项目 | 值 |
|---|---|
| 端口 | Windows 下为 USB-CDC 虚拟 COM（插上后设备管理器新增） |
| 波特率 | 921600（DMTool 默认） |
| 数据位 | 8 |
| 校验 | None |
| 停止位 | 1 |
| 流控 | None |

> 921600 是主机侧串口参数；CAN 总线本身是 **1 Mbps**。两者不是一回事。

## 2. 配置/控制命令

| 功能 | 字节 | 说明 |
|---|---|---|
| 设置串口波特率 | `55 AA` + baudrate[4] + databit + stopbit + parity + `AA 55` | 11 字节；具体字节序待确认 |
| 设置 CAN 波特率 | `55 05 <index> AA 55` | index 0 = 1000 kbps |

## 3. TX：30 字节 CAN 发送帧

```text
55 AA 1E CMD N[4] T[2] IDTYPE RES[2] CANID[2] FRAMETYPE IDACC DATAACC DLEN RES[2] DATA[8] CRC
```

| 偏移 | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 0–1 | 帧头 | 2 | `55 AA` |
| 2 | 帧长 | 1 | `1E` = 30 |
| 3 | 命令 | 1 | `01` 发送数据帧（真机可用）；`02` 握手；`03` 无回显转发（本固件未验证成功） |
| 4–7 | 发送次数 | 4 | 小端；`FFFFFFFF` = 无限 |
| 8–9 | 间隔 | 2 | 小端，单位 ms |
| 10 | ID 类型 | 1 | `00` 标准；`01` 扩展 |
| 11–12 | 保留 | 2 | 必须为 `00 00` |
| **13–14** | **CAN ID** | **2** | **小端；真机确认的位置** |
| 15 | 帧类型 | 1 | `00` 数据；`01` 远程 |
| 16 | idAcc | 1 | 默认 0 |
| 17 | dataAcc | 1 | 默认 0 |
| 18 | 数据长度 | 1 | 0–8 |
| 19–20 | 保留 | 2 | `00 00` |
| 21–28 | CAN 数据 | 8 | 不足补 0 |
| 29 | CRC | 1 | 本固件 `00` 可用 |

> **真机确认（2026-11-20，DM-USBCU1 + 2×G6220）**：
> - CAN ID 必须按 **2 字节放在 13–14**；官方字段表写的 4 字节（11–14）在本固件上会把 ID 读成 0，电机不响应。
> - `cmd=0x01` 可用；`cmd=0x03` 试过没有响应。
> - CRC 固定 `0x00` 可用。
> - DLEN 在偏移 18；19–20 保留。

### 真机已验证的完整往返

读电机 1（CAN ID 0x01）的 RID 0x50（位置）：

```text
TX: 55 AA 1E 01 01 00 00 00 0A 00 00 00 00 FF 07 00 00 00 08 00 00 01 00 33 50 00 00 00 00 00
AC: AA 12 08 FF 07 00 00 01 00 33 50 00 00 00 00 55
RX: AA 11 08 11 00 00 00 01 00 33 50 72 3D 33 C0 55
```

- `AC` 是模块的发送成功回执（`cmd=0x12`）。
- `RX` 是电机 1 的反馈（`cmd=0x11`，CAN ID 0x11）。
- 响应数据 `01 00 33 50 72 3D 33 C0`：CAN ID=0x01，命令 0x33，RID=0x50，值 `0xC0333D72` = **-2.8006 rad**。

### Python 参考实现

```python
def pack_usb2can_frame(can_id: int, data: bytes) -> bytes:
    assert len(data) <= 8
    f = bytearray(30)
    f[0:2] = b"\x55\xAA"
    f[2] = 0x1E
    f[3] = 0x01                    # 真机确认：0x01 可用
    f[4:8] = (1).to_bytes(4, "little")
    f[8:10] = (10).to_bytes(2, "little")
    f[10] = 0x00                   # standard
    f[11] = 0x00                   # reserved
    f[12] = 0x00                   # reserved
    f[13] = can_id & 0xFF          # CAN ID low
    f[14] = (can_id >> 8) & 0xFF   # CAN ID high
    f[15] = 0x00                   # data frame
    f[16] = 0x00                   # idAcc
    f[17] = 0x00                   # dataAcc
    f[18] = len(data)              # DLEN
    f[19:21] = b"\x00\x00"
    f[21:29] = data.ljust(8, b"\x00")
    f[29] = 0x00                   # CRC
    return bytes(f)
```

> `DM_CAN.py` 的模板用 `cmd=0x03`，在另一版固件/模块上可用；本机固件实测要用 `cmd=0x01`，并保持 CAN ID 在 13–14。

## 4. RX：16 字节 CAN 接收帧

```text
AA CMD FORMAT CANID[4] DATA[8] 55
```

| 偏移 | 字段 | 说明 |
|---:|---|---|
| 0 | 帧头 | `AA` |
| 1 | 命令 | `11` 收到 CAN；`12` 发送成功；`01/02` 失败；`00` 心跳 |
| 2 | 格式 | bit0–5 数据长度；bit6 扩展帧；bit7 远程帧 |
| 3–6 | CAN ID | 32-bit 小端 |
| 7–14 | 数据 | 固定 8 字节 |
| 15 | 帧尾 | `55` |

### 示例

```text
AA 11 08 00 00 00 00 00 01 02 03 04 05 06 07 55
```

解析：

- 命令 `11`：收到 CAN 帧；
- 格式 `08`：数据长度 8，标准数据帧；
- CAN ID `0x00000000`；
- 数据 `00 01 02 03 04 05 06 07`。

### 解析器要点

- 串口是字节流，必须自己切帧：找 `0xAA`，凑够 16 字节，检查尾字节 `0x55`；不匹配则丢弃 1 字节重新同步。
- `FORMAT` 的低 6 位是有效数据长度（0–8）；不要假设总是 8。
- 扩展帧/远程帧在电机控制中不用，但要能解析并记录。
- 命令 `11` 才进入电机反馈；其他命令用于诊断/错误计数。
- 串口读线程与写线程分离；读线程只解析、入队。

## 5. 与电机 MIT 协议的关系

USB2CAN 只是把 8 字节 CAN 载荷封装/解封；电机协议不变：

- 使能：CAN ID = 电机 ID，数据 `FF FF FF FF FF FF FF FC`
- 失能：`... FD`
- 设零：`... FE`
- 清错误：`... FB`
- MIT：`pos[16] | vel[12] | kp[12] | kd[12] | tau[12]`
- 反馈：`status|id` + pos/vel/tau + 温度

因此实现分两层：

```text
DmMotor（MIT/寄存器/使能）  →  can.Message(arbitration_id, data)
SerialUsb2CanBus（55 AA 串口封装） → COM
```

## 6. 带宽预算

| 项目 | 每帧字节 | 2 电机 × 500 Hz | 2 电机 × 1000 Hz |
|---|---:|---:|---:|
| TX（30 B） | 30 | 30,000 B/s | 60,000 B/s |
| RX（16 B） | 16 | 16,000 B/s | 32,000 B/s |
| 合计 | 46 | 46,000 B/s | 92,000 B/s |
| 921600 8N1 理论 | — | 92,160 B/s | 92,160 B/s |
| 占用 | — | **约 50%** | **约 100%** |

结论：**默认 500 Hz**。1 kHz 在 921600 下没有余量，而且还要留给串口协议/重传/其他帧。除非模块支持更高的串口速率，否则不要设 1 kHz。

**实测（2026-11-20，双电机 MIT 保持，1500 周期）**：实际 **500.0 Hz**，p99 周期 **2.778 ms**，**0 overrun**，每轴 **1501 帧**反馈，**3002** 个发送回执，**0 坏帧**。500 Hz 在 Python 线程 + 独立 RX 线程下可行。

> 如果模块的 USB-CDC 实际不按 921600 限速，理论上 USB 全速 12 Mbps 足够；但 DMTool 默认 921600，先按保守值设计，实测后再提高。

## 7. 协议确认结果与抓包方法

### 已确认（2026-11-20，DM-USBCU1 + 2×G6220）

- `cmd=0x01` 可用；`cmd=0x03` 在本固件上没有响应。
- CAN ID 必须按 **2 字节放在 13–14**；把 0x201 写成 4 字节 `01 02 00 00` 放在 11–14 时，模块把 ID 读成 0，电机不响应。
- DLEN 在偏移 **18**；19–20 保留。
- CRC 固定 `0x00` 可用。
- 模块对每帧回 `AA 12 ... 55` 发送成功；电机反馈是 `AA 11 ...`，CAN ID 为 Master ID（0x11/0x12）。
- 心跳 `55 04 AA 55` 和 CAN 波特率命令 `55 05 00 AA 55` 在本机没有回包；可能不需要，或需要特定时机。先以 30 字节数据帧为准。
- 实际可用帧见第 3 节“真机已验证的完整往返”。

### 如果换模块/固件，仍需抓包

官方例程末字节是 `0x88`，本机 `0x00` 可用；不同固件可能有 CRC 校验。若通信失败，按以下方法抓包：

**方法 A：DMTool 的 CAN 页**  
只能看解码后的 CAN 帧，不能看串口封装；适合确认电机协议。

**方法 B：USB2CAN 工具手动发送**  
适合确认 CAN 层，不知道串口层。

**方法 C：串口抓包（推荐）**  
用 com0com 建一对虚拟串口，DMTool 连虚拟口 A，代理程序转发到真实 USB2CAN 的 COM 口并记录原始字节。

```text
DMTool → COM_A(虚拟) → capture proxy → COM_B(真实 USB2CAN) → CAN
                     ← 记录原始字节 ←
```

**方法 D：USBPcap + Wireshark**  
抓 USB CDC 流量，能拿到串口字节，但解析更麻烦。

确认新固件的 CRC 时，抓 DMTool 发同一 CAN 帧的原始字节，对比末字节；再尝试 CRC8（poly 0x07/0x31/0x9B）或求和/异或，并把结果写成 golden vector 单元测试。

### 连续旋转/编码器补充

- 16-bit MIT 反馈位置在 **±12.5 rad** 回绕。
- RID **0x50 `p_m`** 是**多圈绝对位置**，不回绕；实测 yaw 从 +8.39 连续到 -14.15。
- RID **0x51 `xout`** 读回 0.0，本机型不可用。
- yaw 连续旋转实测：-0.5 rad/s × 45 s，1 次 wrap，累计 -22.38 rad（-3.56 圈）；最大速度 0.582 rad/s，最大力矩 0.0464 N·m。
- 正向 +0.5 rad/s × 45 s 同样通过：从 raw +10.86 出发，在 +12.5 回绕，累计 +22.42 rad（+3.57 圈），最大速度 0.560 rad/s、力矩 0.0415 N·m。
- 此前 +10 rad 附近的 0.696 N·m 尖峰是外部触碰，不是机械/控制问题。
