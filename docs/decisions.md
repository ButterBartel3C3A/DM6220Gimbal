# 技术选型记录（ADR）

本文件记录当前阶段已经确定的架构决策。后续若因硬件或实测结果改变，追加新的 ADR，不直接改历史结论。

## ADR-001：使用 Python 3.11+，控制环独立线程

**状态**：已接受（2026-11-19）

**背景**
- 上位机需要快速迭代、方便 AI/网络接口集成、方便做数据记录与可视化。
- 控制对象是双轴云台，机械带宽低；真正的高频电流环在电机驱动器内部。
- Windows 上 Python 的定时抖动是主要风险。

**决定**
- 语言使用 Python，最低 3.11；当前环境 3.13 可用，`pyserial`/`python-can` 均支持 3.13（`dmcan-sdk` 备选后端也声明支持 3.9–3.13）。
- 控制环放在**独立线程**，不使用 asyncio 驱动；默认 500 Hz，可配置到 1 kHz。
- 使用 `time.perf_counter()`、`timeBeginPeriod(1)`、混合 sleep + 自旋等待，并统计抖动。
- 控制环热路径只做简单浮点运算和 CAN 发送，不写日志、不做 JSON、不碰 UI。
- 若实测 1 kHz 抖动不可接受，保留将控制核心下沉到 C++/Rust（pybind11/PyO3）的选项，但不作为第一版。

**后果**
- 开发速度快，AI/HTTP/MCP 生态成熟。
- 500 Hz 下控制周期 2 ms；2026-11-20 实测 **500.0 Hz、p99 2.778 ms、0 overrun、0 坏帧**（双电机 MIT 保持，1500 周期）。
- 串口 921600 8N1 下，两电机 500 Hz 的 30B TX + 16B RX 已占约 50% 带宽；1 kHz 不可行，除非确认模块支持更高串口速率。
- 不在 PC 上实现高频电流环；电流环由驱动器 FOC 完成。

## ADR-002：CAN 传输优先使用串口型 USB2CAN（`55 AA` 帧），USB2CANFD 作为备选后端

**状态**：已接受（2026-11-19），2026-11-19 根据实物工具修正

**背景**
- 桌面的 `DMTool-v2.1.9.4.exe` 进程名为 `serial-port-assistant`，连接界面是 **COM 口 + 921600 8N1**；底部状态直接显示 `USB2CAN`。
- `USB2CAN_2.0.0.3.exe` 同样是串口工具：左侧选择 COM/波特率/数据位/校验/停止位，右侧发送 CAN ID + 8 字节数据。
- Seeed Studio 的达妙电机教程把 **这两个完全相同的 exe** 作为一套方案，并明确使用 DMTool 的串口连接。
- 因此当前实物大概率是 **DM-USBCU1 一类串口型 USB2CAN**，不是 libusb 型 USB2CANFD。
- 串口型模块的 CAN 数据封装为 30 字节 TX 帧（`55 AA 1E ...`）和 16 字节 RX 帧（`AA ... 55`），详见 `docs/usb2can-serial.md`。
- 2026-11-20 真机确认：**COM10**（VID_2E88/PID_4603），可用帧为 `cmd=0x01`、**CAN ID 2 字节放在 13–14**、`DLEN@18`、`CRC=0`；`cmd=0x03` 在本固件无响应。
- `python-can` 仍是合适的上层抽象，自带 virtual 接口，方便无硬件测试。

**决定**
- **主后端**：`pyserial` + `SerialUsb2CanBus(can.BusABC)`：
  - 打开 COM 口，默认 **921600, 8N1**；
  - `send()` → 构造 30 字节 `55 AA` 帧 → `serial.write()`；
  - 串口读线程 → 按 `AA ... 55` 解析 16 字节 RX 帧 → `queue.Queue` → `_recv_internal()`；
  - 启动时发送 CAN 波特率设置 `55 05 00 AA 55`（index 0 = 1 Mbps）和心跳 `55 04 AA 55`，具体是否需要以实测为准。
- **备选后端**：`DmCanBus(can.BusABC)` 包装 `dmcan-sdk` 2.1.x（`libdmcan` 2.1.0，固件 V2.0.0+），用于 USB2CANFD_S/D/LinkX4C。
- 电机层只依赖 `can.BusABC`，不直接依赖 `pyserial` 或 `dmcan-sdk`。
- 同时提供：
  - `SocketCanBus`（Linux 备选，`python-can` 原生）
  - `virtual` 总线（测试/仿真）
- 后端选择由配置 `can.backend: serial_usb2can | dmcan | socketcan | virtual` 决定；启动时记录实际串口/设备信息。
- 串口型后端不依赖 `libdmcan`；`vendor/dmcan/` 仅用于 USB2CANFD 备选。

**后果**
- 主要依赖变为 `pyserial`，部署简单（Windows 10 自带 USB-CDC 驱动，插上后出现 COM 口）。
- **带宽成为硬约束**：30 字节 TX + 16 字节 RX 每帧；两台电机 500 Hz 约 46 KB/s，921600 8N1 理论 92 KB/s，已占约 50%；1 kHz 会打满。默认 500 Hz，不建议 1 kHz。
- 2026-11-20 实测双电机 500 Hz：**500.0 Hz、p99 2.778 ms、0 overrun、每轴 1501 帧、0 坏帧**，确认 Python 控制线程 + 独立 RX 线程可行。
- 55 AA 帧已确认：`cmd=0x01`、CAN ID@13–14、DLEN@18、CRC=0 可用；`cmd=0x03` 在本固件无响应。
- 若换用 USB2CANFD，切换到 `dmcan` 后端即可，电机/控制/API 层不变。

**备选方案**
- 直接用 `dmcan-sdk`：仅适用于 USB2CANFD，不适用于当前串口型工具。
- 用 `slcan`：不适用，达妙串口型 USB2CAN 是私有 `55 AA` 协议，不是 LAWICEL。
- 用 Seeed `motorbridge`：Windows 后端要求 PEAK PCAN，不匹配达妙原生模块。

## ADR-003：自行实现达妙 MIT 驱动，不依赖现成第三方电机库

**状态**：已接受（2026-11-19）

**背景**
- `damiao-motor`（jia-xie）只面向 Linux SocketCAN，且型号表没有 G6220。
- `DM_Control_Python` 的 `DM_CAN.py` 提供了串口型 USB2CAN 的 `55 AA` 帧参考，但其控制 API、型号表和线程模型不适合直接作为本项目的运行时核心。
- LeRobot 的 Damiao 驱动有 G6220 参数，但绑定 LeRobot 的机器人抽象，直接引入过重。
- 达妙 MIT 协议帧格式固定、公开，自己实现工作量可控。

**决定**
- 自行实现：
  - MIT 帧编码/解码（16-bit 位置，12-bit 速度/Kp/Kd/力矩）
  - 反馈帧解码（位置、速度、力矩、温度、状态码）
  - 使能/失能/设零/清错误
  - 0x7FF 寄存器读写（控制模式 0x0A、MST_ID 0x07、ESC_ID 0x08 等）
- G6220 参数单独建模；2026-11-20 已从两台电机读回，均一致：
  - `P_MAX = 12.5 rad`（RID 0x15）
  - `V_MAX = 45 rad/s`（RID 0x16；DMTool 滑块默认 30 只是界面默认值）
  - `T_MAX = 10 N·m`（RID 0x17）
  - `NPP = 14`，`Gr = 1.0`（RID 0x10 / 0x14）
  - `Kp ∈ [0, 500]`，`Kd ∈ [0, 5]`
  - 编码器 16-bit（65536）
  - `KT_Value = 0.0`：MIT 位置保持（Kp/Kd）已验证；纯力矩 `tau_ff` 仍需单独验证
- 协议实现只依据公开文档，不复制第三方代码；如后续参考开源实现，保留许可证声明。

**后果**
- 完全掌控协议细节和错误处理。
- 需要自己写协议测试（golden vectors）和真机验证。
- `T_MAX` 是 MIT 力矩映射范围，不等于电机物理峰值扭矩；安全力矩限制单独配置（建议先 ≤ 2.0 N·m）。

## ADR-004：控制结构采用“PC 位置环 + 驱动器电流环”，可选速度环

**状态**：已接受（2026-11-19）

**背景**
- 需求是“尽量实现串级 PID（位置环外环—电流环内环）”。
- MIT 模式下，上位机只能下发 `p_des, v_des, Kp, Kd, tau_ff`；驱动器内部完成 MIT 控制律和 FOC 电流环。
- 无法直接读取/给定 `iq`，也无法绕过驱动器的电流环。

**决定**
- **硬件 bring-up 阶段先用 `impedance`**：MIT 内部 PD + 电流环。2026-11-20 已验证：yaw `Kp=0.5, Kd=0.1` 保持稳定；pitch 有重力/摩擦，需 `Kp=3.0, Kd=0.3`，0.03 rad 小步静差约 0.005–0.008 rad。
- 最终默认模式 `pos_current`：
  1. 上位机位置 PID（可带微分阻尼、积分抗饱和、重力前馈）输出力矩给定 `tau_cmd`；
  2. MIT 帧使用 `Kp=0, Kd=0, tau_ff=tau_cmd`（纯力矩模式）；
  3. 驱动器 FOC 电流环作为内环跟踪该力矩对应的 `iq_ref`。
  4. `KT_Value=0.0` 不影响 `tau_ff`：2026-11-20 在 yaw 上 0.05 N·m 指令产生约 0.0415 N·m 反馈并明显加速，**纯力矩路径已验证**；下一步做 PC 位置环整定和力矩标定。
- 可选模式 `pos_vel_current`：
  - 位置 PID → 速度给定 → 速度 PID → 力矩给定 → 驱动器电流环。
  - 速度反馈做低通滤波；适合位置环出现抖动/超调时。
- 可选模式 `impedance`：
  - 直接下发 `p_des, v_des, Kp, Kd, tau_ff`，利用驱动器内部 MIT PD + 电流环。
  - 适合安全保持、遥操作、参数未标定阶段。
- 不默认在 PC 上再做一层“力矩/电流 PI”包住驱动器电流环；这会引入额外延迟和噪声，且内环对象未知。若要做实验，作为独立开关，默认关闭。

**后果**
- 这是 MIT 协议下能实现的、物理上合理的串级结构。
- 位置环增益、滤波器、力矩限幅必须现场整定；初始值只作保守起点。
- 需要记录阶跃响应，用于调参与验收。

## ADR-005：常驻 daemon + HTTP/WebSocket + MCP，而不是让 AI 直接持有串口

**状态**：已接受（2026-11-19）

**背景**
- USB-CAN 设备通常被一个进程独占；GUI、CLI、AI 不能各自打开设备。
- AI 需要稳定的、可审计的、带安全约束的控制接口。

**决定**
- `gimbald` 常驻进程独占硬件，负责控制环、状态机、安全、遥测。
- 对外只暴露本地 HTTP/WebSocket API（默认 `127.0.0.1:8765`）。
- 三个客户端：
  - Web UI
  - CLI（Typer）
  - MCP Server（stdio，作为 daemon 的 HTTP 客户端）
- 所有控制命令进入同一个命令邮箱；连续目标（attitude/joint）采用“覆盖最新值”，离散命令（enable/disable/estop）采用队列。
- 安全层在 daemon 内，AI 无法绕过限幅、TTL、软限位、温度/反馈超时保护。
- 审计日志记录来源（ui/cli/mcp）、命令、参数、时间、结果。

**后果**
- 只有一个进程碰硬件，状态一致。
- AI 和人类共享同一套安全边界。
- MCP 不需要知道 CAN 细节；换硬件不影响 AI 接口。

## ADR-006：第一版 UI 用本地 Web，不先做 Qt 桌面端

**状态**：已接受（2026-11-19）

**背景**
- 需要姿态/关节/力矩/温度实时曲线、使能与急停、PID 调参。
- 桌面 GUI（PySide6 + pyqtgraph）开发量更大，且与 daemon 仍需 IPC。

**决定**
- 第一版使用 FastAPI 提供静态页面 + WebSocket 遥测；前端用原生 HTML/JS + Chart.js，避免 Node 构建链。
- 页面仅监听 localhost。
- 后续如需桌面窗口，用 pywebview 包一层，或另写 PySide6 客户端，复用同一 HTTP API。

**后果**
- 跨平台、零安装客户端、AI 与 UI 共用接口。
- 复杂 3D 可视化后续再引入 Three.js。

## ADR-007：配置、标定与安全参数分离

**状态**：已接受（2026-11-19）

**背景**
- 电机 CAN ID、反馈 ID、零点、方向、软限位、PID 增益都依赖具体硬件和装配。
- 这些值不应散落在代码里，也不应把某一台设备的标定提交到 Git。

**决定**
- `config/gimbal.example.yaml` 作为模板提交。
- 本地 `config/gimbal.yaml`、`config/calibration.yaml` 被 `.gitignore` 忽略。
- 用 Pydantic 做启动校验：ID 范围、限位关系、控制频率、力矩上限、温度阈值。
- 标定优先使用**软件零偏**，避免频繁写电机 flash（擦写寿命约 1 万次）；只有在产线标定时才调用“设零”并存储。
- 安全参数有硬上限，配置文件不能把力矩/温度/速度上限改到危险值之外。

**后果**
- 换一台云台只需换本地配置。
- 配置错误会在启动时失败，而不是上电后乱动。

## ADR-008：连续偏航使用 unwrapped 反馈 + `p_m` 慢速重同步

**状态**：已接受（2026-11-20，基于真机连续旋转测试）

**背景**
- 云台 yaw 轴带滑环，可连续旋转；pitch 轴仍是有限行程。
- 2026-11-20 实测：16-bit MIT 反馈位置在 **±12.5 rad** 回绕；RID 0x50 `p_m` 是**多圈绝对位置**，不随 ±12.5 回绕；RID 0x51 `xout` 读回 0.0，不可用。
- 连续旋转测试：-0.5 rad/s × 45 s，1 次 wrap，累计 -22.38 rad（-3.56 圈），最大速度 0.582 rad/s、力矩 0.0464 N·m。

**决定**
- yaw 控制使用**连续角度**，不使用 16-bit 原始位置直接做 PID：
  1. 每个控制周期用 16-bit 位置，跨 ±12.5 时加/减 25 rad，维护 `yaw_unwrapped`；
  2. 以 1–5 Hz 读取 `p_m`（0x50），与 `yaw_unwrapped` 做慢速重同步（例如一阶低通/限幅修正），避免长时间丢帧后的累计误差；
  3. 目标 yaw 也用 unwrapped 角度；`yaw_continuous: true`，软限位只做数值保护；
  4. pitch 保持有限软限位和 ±12.5 映射。
- 在状态快照中同时暴露：
  - `yaw_unwrapped`（控制用，rad，可超过 ±2π）；
  - `yaw_raw`（16-bit 反馈解码值，±12.5）；
  - `yaw_abs`（`p_m`，多圈绝对）。
- 连续旋转时目标/轨迹角度不做 2π 归一化；UI 显示可归一化，但控制内部保持连续。

**后果**
- 控制层必须实现 wrap 检测和重同步；单元测试要覆盖 ±12.5 边界、连续多圈、丢帧后重同步。
- `p_m` 读取会增加串口流量；1–5 Hz 足够，不要放到 500 Hz 控制环里。
- yaw 角度会持续增长，使用 float64；长时间运行注意数值范围（实际不可能达到）。
- 正反两个方向各 45 s 连续旋转均已通过；此前 +10 rad 附近的 0.696 N·m 尖峰确认是外部触碰，不是机械/控制问题。
- 连续 yaw **不要用 `impedance` 直接下发跨 ±12.5 的 `p_des`**；MIT 位置字段会回绕。连续 yaw 用 `pos_current`（PC 位置环给力矩）或速度模式。

## ADR-009：安全限速使用位置差分速度；默认先 `impedance`

**状态**：已接受（2026-11-20，基于闭环整定记录）

**背景**
- DM 电机在近零速时速度遥测噪声很大：位置几乎不动，原始速度尖峰可达数 rad/s。
- pitch 轴惯量极小：开环 +0.03 N·m 在 0.06 s 内达到 +1.13 rad/s；disabled 时会因重力缓慢下落。
- `pos_current` 高增益会让低惯量轴快速超速（实测 27–36 rad/s）；低增益又无法稳定托住 pitch。
- 用户要求实际速度不超过 1 rad/s。

**决定**
- 1 rad/s 限速使用**位置差分速度**：50 ms 窗口 + 10 Hz 低通；yaw 使用 unwrapped 位置，避免 ±12.5 rad 回绕误判。
- 原始速度只保留 **5 rad/s** 兜底，用于快速识别真正的失控。
- 默认控制模式改为 **`impedance`**（MIT 内部 PD + 驱动器电流环），已验证在部分角度稳定。
- `pos_current` 代码保留，但在 pitch 机械配平/重力前馈标定、增益整定完成前不作为默认。
- `estop` 仍为立即 0 力矩 + 失能；由于 pitch 不平衡，失能后可能下落，现场必须有机械支撑或配重。

**后果**
- 避免速度噪声导致的误触发，同时保留对真实超速的快速保护。
- 默认系统可安全完成保持、小角度阻抗运动；连续 yaw 跨回绕仍需 `pos_current` 或速度模式。
- pitch 的机械配平/重力前馈是后续整定的前置条件。

## ADR-010：出现 ~46 Hz 高频振动后停测，先机械排查再低增益复测

**状态**：已接受（2026-11-20，故障停测）

**背景**
- 两轴同时 MIT 位置正弦（±0.2 rad / 4 s，yaw Kp=1.5/Kd=0.3，pitch Kp=3.0/Kd=0.3）+ 人工随机阻力。
- 运行数秒后出现强烈振动/噪音；位置差分速度仍 <1 rad/s，但原始速度尖峰 10–13 rad/s，力矩 RMS 从 ~0.03 升至 ~0.16 N·m。
- 100 Hz CSV 显示故障段高频速度 RMS 3–6.5，主导频率约 46 Hz（可能 46/54 Hz 附近），两轴同时出现；起始时间 6.5–33 s，与外部阻力/扰动相关。
- 46 Hz 远低于 500 Hz 控制环，属于驱动器内部 MIT/电流环或机械共振/摩擦极限环，不是 PC 轨迹频率。

**决定**
- **立即停测并下电**；不自动重启，不继续向电机发指令。
- 复测前必须检查机械：电机/云台/负载紧固、滑环/中空轴间隙、线缆/接插件、框架共振。
- 复测必须从低幅度、低增益开始（例如幅度 0.05–0.1 rad；yaw Kp=0.3–0.5/Kd=0.1–0.2；pitch Kp=1–3/Kd=0.2–0.3），并使用软性阻尼/摩擦，不要直接抓持。
- 不得把本次测试的高增益写入默认配置；默认保持已验证的 `impedance` 低增益。
- 若 46 Hz 仍出现，读取/调整驱动器 `I_BW`、`V_BW`、`Deta`、`KP_ASR/KI_ASR`，或降低 MIT Kp/Kd，必要时评估 notch/低通。

**后果**
- 连续正弦测试暂停，直到机械检查和低增益复测完成。
- 现有安全层仍需保留：位置差分 1 rad/s（测试脚本 0.98）、原始速度高兜底、力矩/位置/温度/反馈超时保护。
- 记录保留在 `recordings/`，供后续频谱对比。

**后续台架验证（2026-11-20）**
- 台架周期 8 s、高增益、无负载：30 s 干净。
- 台架周期 8 s + 软负载阶跃：t≈19.2–19.5 s 先出现 yaw 误差/力矩上升，约 0.3 s 后 HF 0.06→0.52→1.0。
- 台架周期 4 s、高增益、无手挡：约 12.3 s 后自激，HF 逐渐升到 1.0。
- 结论修正：振动由**工作点稳定裕度 + 外部负载阶跃**共同决定；不是 PC 积分项（本次为 impedance），也不是单纯手持/机械松动。后续优先增加堵转/负载检测、降低 MIT 增益/幅度，并在稳定工作点上逐步加载验证。

**速度模式对照（2026-11-20）**
- 速度正弦 `A=0.314 rad/s, T=4 s`，30 s 无负载：HF 0.02–0.03，干净。
- 同轨迹 + 软负载：45 s，yaw 力矩峰值 0.42 N·m，HF 仍 0.02–0.03，无 46 Hz、无异常位置漂移。
- 同最大速度/加速度的 MIT 位置正弦：台架约 12 s 后自激。
- 结论：驱动器速度/电流环稳定，主要差异是 **MIT 位置环**。后续控制架构优先改为 `pos_vel_mit`（PC 位置环 → MIT `v_des` → 驱动器速度/电流环），或显著降低 MIT 位置 `Kp/Kd`；不再使用当前 MIT 位置高增益组合直接承受负载。

## ADR-011：生产控制只保留位置-速度双环，移除 MIT 模式

**状态**：已接受（2026-11-20，用户明确要求）

**背景**
- 2-DOF 云台不需要 MIT 的阻抗/柔顺能力；位置-速度双环更接近伺服云台常规用法。
- 真机对照：速度模式在 0.42 N·m 软负载下 45 s 稳定，HF 0.02–0.03；MIT 位置 PD 在同速/同负载下出现 46 Hz。
- MIT 位置环没有 PC 积分项，振动也不是 PC PID 积分限幅；问题集中在 MIT 位置 PD 路径。
- POS_VEL 基线（0.2 rad/4 s）已无 46 Hz，但 yaw 出现约 6 Hz 小振荡；将 yaw `KP_APR` 从 54 降到 20 后，5–7 Hz 峰值 0.123→0.018，HF 中位数 0.239→0.044，带载 0.97 N·m 无 6/46 Hz。

**决定**
- 生产 `service/config` 只保留两种模式：
  - `pos_vel`（默认）：`0x100+ID`，位置目标 + 速度限幅；驱动器位置环→速度环→电流环。
  - `velocity_pos`：PC 位置 PID → `v_des`；`0x200+ID` 驱动器速度环→电流环。
- 删除 `impedance` / `pos_current` / `pos_vel_current` 三个 MIT 控制模式。
- `protocol.encode_mit` 和 `DmMotor.send_mit` 仅保留给历史 bring-up/对照脚本，不进入 service。
- 默认 `velocity_limit_rad_s` 降到 **0.8 rad/s**，为 POS_VEL 位置环瞬态留出余量；用户要求上限 1 rad/s。
- `set_pid` 在 `pos_vel` 下拒绝修改（驱动器内部环用 DMTool 调），在 `velocity_pos` 下修改 PC 位置 PID。

**后果**
- 控制架构更简单、可解释：不再有 PC PID 与驱动器 MIT PD 的职责重叠。
- yaw 的 `KP_APR=20` 已写入 `motors.yaw.position_kp_apr`，service 在 `pos_vel` enable 时写入 RAM；如需掉电保持，用 DMTool 存储。
- 后续如负载/温度变化导致 6 Hz 回潮，再微调 `KP_APR`/`Deta`/`V_BW`，或切 `velocity_pos`。
- MIT 仅作为历史资料，不再默认/生产使用。
